# NVIDIA 0.11.3 vs 0.12.0: p894, two-step distilled

## Results

Three measured warm runs per release. Values are medians; ranges show all runs.

| Version | Whole job (s) | Range (s) | Frames/s |
| --- | --- | --- | --- |
| 0.11.3 | 164.64 | 162.95–169.90 | 32.25 |
| 0.12.0 | 163.73 | 163.64–164.48 | 32.43 |

The new release takes 0.6% less time by the medians. The 0.92 s difference is
smaller than the observed run variation, and the ranges overlap. Full-job
performance is effectively similar in this small comparison.

| Metric | 0.11.3 median | 0.12.0 median |

| Total LTX | 159.0 s | 158.1 s |
| Scan | 10.5 s | 10.2 s |
| Encode | 38.2 s | 37.3 s |

| Compose | 53.7 s | 51.9 s |
| Logged warm window-step | 0.50 s | 0.57 s |
| Peak Torch VRAM | 17155.9 MiB | 17496.0 MiB |

The complete denoise pass increases from 57.0 to 58.4 s (+2.5%), while other
stages offset that on this clip. Logged warm rates increase from 0.50 to 0.57
s/window-step; differences in progress timing prevent assigning that
14% logged-rate change to a single cause. Peak Torch VRAM increases by
340.1 MiB. Stage medians are calculated independently.

All six timed runs complete with the same 52 windows at 512 px, 104
window-steps and 48/48 blocks resident. Every timed run reuses compiled GPU
kernels with zero compilation. Both retained warmup outputs pass full decode,
5,310-frame/1080p checks and exact AAC packet preservation.

## Method

Actual licensed frozen Linux releases on RTX 5090, 32 GB, driver 595.104.02,
default 575 W power limit, Core i9-13900K and 62 GiB host RAM. Ordinary desktop
graphics remain active; the shared GPU lock excludes concurrent cooperating ML
jobs. GPU clock and power settings are unchanged.

Input: `~/Downloads/p894-2.mp4`, 177 seconds, 5,310 frames, 1920×1080 at
30 fps, H.264 with AAC audio, 106,594,141 bytes. SHA-256:
`eeed3c2fe6ef55aab6f3c09e8130ff322f86ed8f7a434430aab89e3608791ebc`.
The input and restored videos remain local.

Baseline is the qualified October 20 0.11.3 release (`ed24170`); candidate is
the normal 0.12.0 build from `c65c28a`. Executable/core
hashes are freshly checked against the preceding build qualification. The model
hash qualification from the earlier comparison is reused, with file sizes
rechecked. Both use their matching Standard distilled two-step INT8
release checkpoint and byte-identical VAEs. Trial weights are not used.
Artifact identities and build qualification are recorded in the
[earlier comparison](2026-10-24_nvidia_0113_vs_0120_warm.md).

Settings: seed 1234, RF-DETR v6, explicit detector batch size 4, max clip size 90,
temporal overlap 8, HEVC CQ18/preset p4, no secondary restoration, Large output
off and Lesser overlap on. Each version receives one excluded full-clip warmup,
then three fresh-process timed runs. Order alternates old/new, new/old, old/new.
Persistent detector and compiler caches are warm; each timed process still
starts its worker and loads the protected models.

## Validation and interpretation

Both retained warmup outputs must pass complete FFmpeg decode, exact frame count
and dimensions, and unchanged AAC packet hash. Each timed output must complete
successfully and be nonempty; the existing benchmark runner then removes it.
Matching window counts, window-steps, precision and 48/48 resident blocks are
required for every timed sample. Failed runs and software fallbacks are rejected.

Wall time measures the whole process. LTX denoise-pass time includes loading and
startup. Progress is timed differently between releases, so logged warm
window-step rates are not a controlled comparison of GPU compute time. Stage
totals are rounded to 0.1 s and warm step rates to 0.01 s in the logs.

Peak VRAM is the application's Torch allocator peak, rather than whole-device
usage. Parent-only resource samples omit part of the workload and are not
used. This compares two complete releases on one clip/GPU; individual runtime
and dependency changes are not controlled separately.

Raw logs, artifact identities and output-validation records are retained locally.
