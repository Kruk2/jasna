# Every-frame mosaic scan per decode backend (v0.8.2, 2026-07-21)

`scripts/benchmark_scan_backends.py`, version 0.8.2 (unreleased), RTX 5090: GUI `MosaicScanWorker` with
`stride_seconds=0.0`, GUI defaults (rfdetr-v6, fp16, batch 4). Wall = decode + detection + final sync
(detector build excluded). RAM/VRAM med/peak of the subprocess (`scripts/bench_memory.py`). Same clips as the
e2e run (SONE 6056 frames, 8K VR 900). The `vali` rows are the scan baseline.

Wall seconds, peaks and pyav VRAM are in `2026-07-21_v0.8.2_scan_decode_backends.csv` / `_scan_vr.csv`;
the two-decoder column (`scan_decoder_count`, same results as one decoder) in `_scan_parallel_decode.csv` /
`_scan_parallel_decode_vr.csv`, VRAM med 1094–2792 MB (5256 at 8K).

The scan is decode-bound: vali beats pyav-hw by 5–8 % at ≤1080p, 13–31 % at 4K and 22 % at 8K, with 100–350 MB
less VRAM; pyav-sw is 2–5× slower. Splitting ≥4K, ≥10 s videos across the RTX 5090's two NVDEC units lifts 4K to
the detection ceiling (~730–770 fps at batch 4; batch 8/16 engines measured 799/691 vs 899 fps).

Strided scans (4097c01) gain too: 1 s interval on 4K hevc 10-bit 11.1 → 5.7 s, 8K VR 5.1 → 3.9 s.
The two-decoder gate stays static (NVIDIA + ≥4K + ≥10 s): no API reports the NVDEC unit count, and extra sessions
never hurt (1→4 sessions: 576, 1026, 1161, 1177 fps aggregate); the cost is 200–400 MB VRAM.
A third decoder would add ~9 % to strided scans; not used.
