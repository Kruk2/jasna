# AMD Radeon AI PRO R9700: LTX end to end, v0.12.2 vs v0.12.3 (2026-11-13)

Radeon AI PRO R9700 (gfx1201, 32 GB) on a rented instance: Core i3-8100 (4 cores), 15 GB RAM, Ubuntu 26.04
(kernel 7.0), PyTorch 2.14.0+rocm10.1.0 (HIP 7.16), ffmpeg 8.0.1, AMF 26.20 for decoding and HEVC encoding.
v0.12.2 is tag `v0.12.2` (`12510264`), v0.12.3 is main `07f9bc38`; each is a source install (source + its own
venv, same dependency pins) with its own MIOpen user database. Standard LTX (2 steps) with the full VAE encoder
and decoder, on placeholder weights (`--ltx-trial`: the real model's shapes and step count with random values, so
the same work as a real run, but the output is not restored). Job time is the whole job, measured around the
process. Two clips: S610 (1080p, 6056 frames, 144 windows) and M284 (15 s 1080p30, 449 frames, 5 windows). Each
version first ran one discarded job per clip; the timed jobs ran in the order A B B A per clip. The table shows
the mean of the two runs; per-run values are in the `.csv`.

| Job | v0.12.2 | v0.12.3 |
|---|---|---|
| S610 | 986.7 s | 828.6 s (-158.1 s, -16 %) |
| M284 | 56.0 s | 51.3 s (-4.7 s, -8 %) |

## Where the time goes

| LTX pass (S610) | v0.12.2 | v0.12.3 |
|---|---|---|
| scan | 50.3 s | 40.0 s (-20 %) |
| encode | 180.5 s (1.11 s/window) | 148.1 s (0.99 s/window, -18 %) |
| denoise | 473.5 s (1.59 s/window-step) | 431.8 s (1.44 s/window-step, -9 %) |
| compose | 273.4 s (decode 1.53 s/window) | 198.6 s (decode 1.34 s/window, -27 %) |
| LTX total | 977.6 s | 818.5 s (-16 %) |

| LTX pass (M284) | v0.12.2 | v0.12.3 |
|---|---|---|
| scan | 4.9 s | 4.6 s |
| encode | 10.7 s | 9.9 s |
| denoise | 19.6 s | 18.3 s |
| compose | 11.7 s | 9.4 s |
| LTX total | 46.9 s | 42.1 s (-10 %) |

The time outside the LTX passes (start, detector, model setup, finishing the file) is about 9-10 s per job in
both versions. Every pass is faster in v0.12.3; on the long clip compose gains the most.

## Other notes

- Peak VRAM is the same, 16.9 GB (16895-16899 MiB). Peak RAM (whole system, sampled every 5 s) was about
  6.9-7.0 GB with v0.12.2 and 6.3 GB with v0.12.3 on S610.
- Run-to-run spread is small: the two runs of each version differ by at most 2.8 s (S610) and 0.4 s (M284).
- Discarded first runs: S610 1526.6 s (v0.12.2) and 1265.6 s (v0.12.3), each with the LTX speed test and the
  first kernel searches; M284 74.4 s and 60.0 s, each building the native LTX block's kernels.
- Source installs on Linux need `ROCM_HOME=/opt/rocm` (the system ROCm, same HIP version as PyTorch) to build
  the native LTX block: the compiler inside the PyTorch ROCm wheels does not find the ROCm device libraries, and
  Jasna then falls back to the slower torch.compile path. Release builds ship the block prebuilt. All timed runs
  used the native block; the two S610 first runs ran before this was set, on the fallback path.
- Command, the same for both versions:
  `ROCM_HOME=/opt/rocm python -m jasna --input <clip> --output <out>.mkv --restoration-model-name ltx
  --ltx-vae-encoder full --ltx-vae-decoder full --ltx-trial --log-level info --no-progress`

Not measured: real model weights (output quality), release builds, other AMD GPUs, Windows, Fast mode.
