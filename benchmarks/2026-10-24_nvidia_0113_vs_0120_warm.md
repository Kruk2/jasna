# Linux NVIDIA 0.11.3 vs 0.12.0, warm runs

## Results

Three timed runs per cell; wall values are median [minimum–maximum].

| Mode | 0.11.3 wall (s) | 0.12.0 wall (s) | Wall change |
| --- | --- | --- | --- |
| Standard INT8 | 64.08 [63.16–64.23] | 62.58 [61.55–63.44] | -2.3% |
| Standard Fast NVFP4 | 62.82 [62.22–63.07] | 59.62 [59.49–59.97] | -5.1% |

| Mode / metric | 0.11.3 median | 0.12.0 median | Change |
| --- | --- | --- | --- |
| Standard INT8 / Denoise pass | 17.3 s | 17.6 s | +1.7% |
| Standard INT8 / Warm window-step | 0.48 s | 0.54 s | +12.5% |
| Standard INT8 / Peak Torch VRAM | 14083.8 MiB | 14416.8 MiB | +2.4% |
| Standard Fast NVFP4 / Denoise pass | 14.1 s | 14.1 s | +0.0% |
| Standard Fast NVFP4 / Warm window-step | 0.39 s | 0.45 s | +15.4% |
| Standard Fast NVFP4 / Peak Torch VRAM | 8854.0 MiB | 8963.9 MiB | +1.2% |

Full-job medians improve 2.3% for INT8 and 5.1% for NVFP4. Logged warm
rates increase from 0.48 → 0.54 s/window-step for INT8 (+12.5%) and
0.39 → 0.45 for NVFP4 (+15.4%). These percentages do not isolate a single cause: progress timing also
changes between these releases.
The end-to-end measurements remain comparable; the warm-rate attribution needs
profiling with the same timing boundaries.

All 12 timed runs pass, and all four functional warmups pass full decode, frame
count and audio checks. Every timed run reuses compiled GPU kernels with zero
compilation; the new build reuses 101 kernels in each run. Raw measured samples
are in [the CSV](2026-10-24_nvidia_0113_vs_0120_warm.csv).

## Method

RTX 5090, 32 GB, driver 595.104.02, default 575 W power limit; Core i9-13900K,
62 GiB host RAM. Ordinary desktop graphics remain active; no concurrent ML job.
The shared GPU lock is held throughout the comparison. Clock and power settings
are unchanged.

Both targets are actual licensed, protected frozen Linux releases. Baseline is
the qualified October 20 0.11.3 build (`ed24170`); candidate is the normal
0.12.0 build from `c65c28a2acab5daa1b105696fa0d62c072f67056`. The candidate passes release and archive checks before GPU testing.
Both use their matching release-model checkpoints; trial weights are not used.

Input is `~/Downloads/m284-3.mp4`: 1,138 frames, 1920×1080,
30000/1001 fps, 38.004267 seconds, H.264 with AAC audio. Input SHA-256:
`eff9493a120d4fc88b82989ee445225f51f5223cc397b3e61cb333977acd2bce`.
The video and restored outputs remain local.

Matched settings: Standard distilled two-step LTX, INT8 or Fast NVFP4, seed 1234,
RF-DETR v6, explicit detector batch size 4, max clip size 90, overlap 8,
HEVC CQ18/preset p4, no secondary restoration, Large output off and Lesser
overlap on. Batch size is explicit because 0.12.0 defaults to automatic sizing,
whereas 0.11.3 defaults to 4. VAEs are byte-identical; all eight model/VAE input
files pass full SHA-256 verification against their published hashes.

Each version/precision receives one excluded full-clip warmup, followed by three
fresh-process timed runs. Version order alternates old/new, new/old, old/new.
Warm means persistent compiler and detector caches are populated; process
startup, worker admission and protected model loading still occur in every run.
Every sample renders the same 12 windows at 512 px, 24 window-steps, with all
48 transformer blocks resident. No failure or software-fallback flag is accepted.

## Timing limits

These runs compare complete releases rather than individual runtime changes.

Several runtime changes may affect these timings; their individual contributions
were not measured. Compiled-kernel cache misses are excluded by the run logs.

## Validation and limits

All four retained warmup videos must decode completely, contain all 1,138
1920×1080 frames, and preserve the input AAC packet hash. Timed-run outputs are
checked for successful completion and nonempty output, then removed by the
existing `scripts/benchmark_releases.py` runner.

Wall time covers the full process; LTX denoise time includes startup and loading.
Progress is timed differently between releases, so logged warm window-step
rates are not a controlled comparison of GPU compute time. Stage totals are
rounded to 0.1 s and warm rates to 0.01 s; percentage changes inherit this
rounding. Peak VRAM is the application's Torch allocator peak, rather than
whole-device usage. Parent-only resource samples omit part of the workload
and are not used.

Raw logs, artifact identities and output-validation records are retained locally.
