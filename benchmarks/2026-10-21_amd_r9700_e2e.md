Raw rows: `2026-10-21_amd_r9700_e2e.csv` (one row per timed run; `label` names the config).

  detection became the limit.

## Setup

- **Pod**: privileged Docker, Ubuntu 26.04, 2x Radeon AI PRO R9700 32 GB (gfx1201), ROCm 10.1 system,
  torch 2.12.0+rocm10.0.0, AMF 26.20, Ryzen 7 3800XT (8C/16T), 30 GB RAM.
- **GPUs**: HIP device 1 = `0000:0a:00.0` sits on the CPU's PCIe 4.0 x16 link, and it is also the boot-VGA device
  that AMF always uses. HIP device 0 = `0000:05:00.0` sits behind the chipset's PCIe 3.0 x4 link (3.2 GB/s H2D).
- **Clip**: owner-chosen `p894-2.mp4`, 1920x1080 H.264, 30 fps, 177 s, 5310 frames, AAC. Output 85.2 MiB HEVC
  for every commit. The H.264 constant-QP default from ce1c844 is not exercised, since the default codec is HEVC.
- **Command**: `HIP_VISIBLE_DEVICES=<n> python -m jasna --input p894-2.mp4 --output out.mp4
  --secondary-restoration none --no-progress --log-level info`. Everything else is the CLI default for the commit:
  BasicVSR++, rfdetr-v6, max clip 90, overlap 8, HEVC, fp16, and no `MIOPEN_FIND_MODE`, so HYBRID applies.
- **Harness**: `bench_amd.sh <commit> <label>` archives the commit to `/root/bench/src-<sha9>` (source run;
  `jasna.__file__` is checked) and runs `/root/bench/run.sh`. Optional env: `HIP_DEV`, `RUNS`, `IN`, `BASE`,
  `JASNA_DECODE_BACKEND`, `BENCH_EXTRA_ARGS`.
  - Each config of each tree gets a discarded warm-up, then 2 timed runs.
  - Every run holds both GPU locks and first waits for an idle CPU. The notes record any CPU load from other
    processes during the run.
  - A run is killed after 600 s and retried once; the failed log is kept.
  - AMF errors are counted per run.
  - Venvs: the pod venv up to bcf21b9, then an overlay venv with `comfy-kitchen==0.2.38` added (the amd extra lists
    it; only LTX imports it).
- **Metrics**: `startup_s` = process start to the `Processing` line. `pipeline_s` = `Processing` to
  `VRAM usage at end`, including encoder flush and mux. `fps` = 5310 / pipeline_s. `peak_vram_mib` comes from the
  offloader sampler, and `cpu_s` is user + sys of the process. PSNR/SSIM (ffmpeg, all frames, per-frame stats kept)
  are measured against the baseline r1 output and against the commit's own r1.

HIP-0 is 8 % (baseline) to 31 % (final) slower than the same-device config. This is not a cross-GPU copy: on AMD,
AMF always moves frames through host memory. HIP device 0 does its uploads and downloads over the x4 link, so the
penalty grows as the GPU work shrinks. Use the same-device rows as the realistic numbers.
fb35b10 r2 (39.8 fps) is left out of its mean, because another job's CPU load started during it.

## Other results

- **RF-DETR warm-up at load (3659106; ad63d30 vs fb35b10, HIP 0):** startup +3.8 s, pipeline −3.9 s, wall
  unchanged (130.7 vs 130.6 s). It moves the cost into load and saves nothing end to end.
- **Batch 8 vs batch 4 in HIP 0 (6f058ca vs 0664f7c):** −3 % pipeline, +8 % CPU, +700 MiB VRAM. In the same-device
  config the same switch is worth about 13 % (see the headline).
- **AV1 decode only (fb35b10, HIP 0, 60 s cuts, 1800 frames, 3 reps):**

  | cut | av1_amf total s / steady fps | pyav-sw (dav1d) total s / steady fps |
  |---|---|---|
  | 8-bit | 5.72 / 322 | 5.36 / 341 |
  | 10-bit | 7.97 / 231 | 7.70 / 237 |

  Software is 3–6 % faster, AMF has no real start-up cost (open → first batch 0.15–0.2 s), and both are far above
  what the pipeline consumes.
- **AV1 10-bit end to end (fb35b10, HIP 0, 60 s cut):** auto (av1_amf) 46.4 s, 38.8 fps, 176 CPU s; pyav-sw
  47.1 s, 38.3 fps, 233 CPU s. The speed is the same, and AMF saves 24 % CPU. PSNR between the two is 48.75 dB.

## AMF "CS has been rejected (-22)"

4 of about 49 e2e attempts failed: 3 with HIP 0 and 1 with HIP 1. Each time the AMF Vulkan decoder failed with
`radv/amdgpu: The CS has been rejected (-22)` 9–60 s into processing, then `VideoDecodeError`.

- **Before d2ce12f**, the b9e67b0 pass then hung: one hang lasted 48 min, and the next was killed by the harness
  timeout.
- **After d2ce12f** (the hang fix), 52207ea had no errors in its 7 attempts, so the fix was not exercised here.
- **No contention:** process snapshots at each error show nothing else running.
- **Likely a pod artifact:** a separate stress repro tied the error to AMF on `0a:00.0` on this pod (7 of 13 runs,
  against 0 of 7 with AMF on `05:00.0`), which points at the pod's driver mix rather than Jasna.
- **Logs:** `/root/bench/logs/*.failed.log` and `*amf-cs-rejected*.log` on the pod.

Also thrown away: one run taken without the GPU-1 lock, and one that overlapped an unlocked `ffmpeg` at 785 % CPU.

## Rejected / not worth it

Measured in the sweep at 432ce76 (same device) or earlier on this pod:

- **No easy wins left on this path.** It is GPU-bound: RF-DETR and BasicVSR++ are about 87 % of GPU work and
  already overlap on separate streams. CPU (about 5 of 16 threads) and the GIL (p99 0.9 ms) are not limits.
- Scene-cut detector off the default stream: +9–15 % (worse). It unthrottles detection, which then starves the
  restorer.
- BasicVSR++ on its own stream: 0 %. A second restorer thread / 2 clips at once: x1.01.
- Detector batch 16: 0 to +3 %, +1 GB VRAM. `--max-clip-size 180`: noise, and it changes the output.
- Fused blend kernel, skipping the 2nd decode, zero-copy AMF: blend, decode and encode together are about 11 % of
  GPU work and wait rather than work at 1080p, so the gain is about 0 (4K only).
- MIGraphX (RF-DETR and BasicVSR++): slower on the small sequential calls, ~16 min compile, wrong output on some
  sub-graphs, no `DeformConv`, and no clean Windows path.
- HIP graphs for BasicVSR++: torchvision `deform_conv2d` breaks under capture (24 dB). After the fused kernels the
  model is GPU-bound, so graphs add nothing.
- `torch.compile` end to end: 60–120 s cold compile and runtime Triton, for gains the AOT kernels already deliver.
- TunableOp, bf16 (no faster, worse agreement), channels_last (−10 %), `cudnn.benchmark` (93–110 s first call),
  MIOpen `FAST` find mode (+65 % restore with a cold db).
- VA-API encode: same quality as AMF, and encode is not the bottleneck. It is only worth adding as a fallback
  when the AMF runtime is missing.
- Left over, ≤ 1–2 % each: a fused conv_offset + LeakyReLU in BasicVSR++, the GELU epilogue in RF-DETR, loading
  the two models in parallel. The one sizeable item is RF-DETR backbone LayerNorm/GELU fusion, estimated −3–6 %
  over 1–2 days.
