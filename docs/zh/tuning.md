# 调整 VRAM 和 GPU 占用

Jasna 会自动管理 VRAM: 显存不足时，排队中的帧会临时移动到系统内存，
需要时再移回来。这部分你不需要做任何配置。下面的设置控制处理占用
多少 VRAM 和 GPU 时间。

## 最大片段大小和时间重叠

Jasna 以片段为单位修复马赛克 — 片段是一起处理的一段连续帧。
**最大片段大小**限制片段的最大长度（越长 = 时间一致性越好，VRAM
占用越多）。**时间重叠**用于平滑片段衔接处的接缝；重叠越大，处理
时间越长。重叠超过 `20` 通常没有太大帮助。

推荐起点:

- 在显存允许的范围内使用尽量大的**最大片段大小**。片段越大越稳定，
  而且更快。
- 将**时间重叠**设置在 `8` 到 `20` 之间。
- 保持交叉淡化开启（它没有额外开销 — 复用的是已经处理过的帧）。

以下为一段 1080p 视频、重叠 8、RTX 5090 上的实测值。你的时间会不同，
但趋势一致:

| 最大片段大小 | 时间 | VRAM |
| -------------:| ----:| ----:|
| 30            | 51 秒 | 3.4 GB |
| 60            | 40 秒 | 3.7 GB |
| 90            | 34 秒 | 4.1 GB |
| 180           | 35 秒 | 5.0 GB |
| 360           | 32 秒 | 6.3 GB |
| 720           | 33 秒 | 8.0 GB |

小片段不是更快，而是**更慢**: 重叠部分的帧在每个片段里都要重新处理，
片段越多重复工作越多。超过大约 `180` 之后时间不再改善，只有 VRAM 继续
增长。同样的片段大小下，4K 视频大约多用一半的 VRAM。

```bash
jasna --input input.mp4 --output output.mkv --max-clip-size 90 --temporal-overlap 8 --enable-crossfade
```

## 显存不足？

1. 降低**最大片段大小** — 每一档的代价见上面的表格。
2. 跳过二级修复，或选择更轻量的方案
   （见[对比表格](models.md)）。

关闭模型编译已经不再是节省显存的有效办法: 它只能省下不到 0.5 GB，
却让处理慢约三倍。

## 修复模型编译

在 NVIDIA 上，修复模型会编译为 TensorRT 引擎。你可以禁用它，但基本没有
理由这么做（AMD 始终使用 PyTorch 模型）:

```bash
jasna --input input.mp4 --output output.mkv --no-compile-basicvsrpp
```

同一段 1080p 视频，片段大小 180:

|                    | 时间 | VRAM |
| ------------------ | ----:| ----:|
| 编译（默认）        | 33 秒 | 5.0 GB |
| 不编译              | 107 秒 | 4.6 GB |

无论选择哪个最大片段大小，引擎都相同，因此更改该设置不会再次触发编译。
